# Полный чеклист аудита проекта

Рабочий чеклист живого сайта: PHP без фреймворка, статика генерируется
скриптом, деплой ручной. Около 140 пунктов в 16 категориях.

Ядро самых переносимых пунктов и объяснение, зачем всё это, — в
[`CHECKS.md`](CHECKS.md). Здесь — полная версия с командами.

**Про идентификаторы.** Имена файлов, классов и токенов взяты из реального
проекта. Подставляйте свои: `style.css` — общий файл стилей, `config.php` —
единственный источник настроек и секретов, `send.php` — обработчик форм,
`build.php` — генератор статики. Команды писались под `grep` в корне проекта.

---

## Структура и архитектура

- Все страницы используют единый `header.php` и `footer.php`?
- Нет страниц, закрывающих `</body></html>` вручную вместо подключения футера?
- Все CSS подключаются через переменную страницы в шапке, а не вручную?
- Нет дублирования подключения общего скрипта?

```bash
grep -rln "</body>" --include=*.php . | grep -v footer.php   # должно быть пусто
```

## Конфигурация и хардкод

- Контакты (телефон, email, соцсети) берутся из `config.php`, а не захардкожены?
- Идентификатор аналитики и токены — только в `config.php`?
- При смене телефона достаточно поменять один файл?
- Цены, включая meta description, берутся из константы, а не вписаны в страницы?
- Списки фотографий читаются из папки через `glob()`, а не хардкод-массивом?
- Список статей генерируется скриптом из исходников, а не ведётся вручную?

```bash
grep -rn "+7\s*(\?[0-9]" --include=*.php --include=*.css . | grep -v config.php
grep -rn "@[a-z0-9.-]\+\.\(ru\|com\)" --include=*.php . | grep -v config.php
```

## CSS — консистентность

- Все цвета через переменные, а не хардкод вида `#B8975A`?
- Отступы, шрифты, размеры — из дизайн-системы?
- Нет инлайн-стилей, дублирующих или переопределяющих классы?
- Брейкпоинты соответствуют стандарту, нет случайных `768px` или `1024px`?
- Все страницы корректны на мобильном, горизонтального скролла нет?
- **Конфликты в цепочках подключения.** Для каждого селектора, переопределяемого больше одного раза в цепочке одной страницы (включая правила внутри `@media`): не теряет ли позднее правило смысл раннего значения — особенно `padding-top` и `margin-top`, завязанные на высоту фиксированной навигации? Совпадают ли брейкпоинты между общим и страничным файлом?

```bash
grep -rn "#[0-9A-Fa-f]\{3,6\}" --include=*.css . | grep -v ":root"
grep -rn "style=\"" --include=*.php .
grep -rn "max-width:\s*\(768\|1024\)px" --include=*.css .
```

Отдельно постройте таблицу «страница → цепочка CSS-файлов». Страница с самой
длинной цепочкой — главный кандидат на тихие баги.

## JavaScript — консистентность

- Нет дублирования одной логики в разных файлах (маска телефона, валидация)?
- Все формы используют единую утилиту форматирования телефона?
- Все обработчики проверяют наличие элемента перед навешиванием?
- Нет `querySelector` там, где должен быть `getElementById`?
- `Escape` закрывает только тот оверлей, который открыт?
- Микро-токены не используются для текста?
- Слабые токены прозрачности не используются цветом текста?

```bash
grep -rn "var(--fs-2xs)" --include=*.css --include=*.php .
grep -rn "color:\s*var(--\(ink-\(30\|40\|50\)\|ww-40\))" --include=*.css --include=*.php .
```

В выдаче должны остаться только осознанные исключения — перечислите их прямо
рядом с командой, иначе следующая проверка сочтёт их нарушением.

## Голые селекторы по тегам

Правило, на которое наступили трижды. Глобальные стили на `nav`, `section`,
`footer` молча наследуются любой своей разметкой с тем же тегом.

- Для своей разметки используются `div` с классом, а не семантические теги, застолблённые глобально?
- Новая страница прогнана против списка голых селекторов?

```bash
grep -rn "<nav\|<section\|<footer" --include=*.php .
```

В выдаче должны остаться только настоящая шапка, шапки лендингов и секции
главной. Всё остальное — кандидат на неожиданное наследование.

**Если тег менять нельзя** (разметку пишет генератор): `position: static`
недостаточно. Голый селектор отдаёт ещё `background`, `backdrop-filter`,
`border-bottom` и боковые `padding`. Гасить надо все.

- Все кнопки, открывающие попап-форму, передают контекст?

## Формы — антиспам и приватность

- Есть honeypot или капча? Скрытое поле передаётся обработчику, при заполнении заявка тихо отбрасывается?
- Есть rate limiting?
- Чекбокс согласия есть в каждой форме, не отмечен по умолчанию, блокирует отправку?
- Серверная подстраховка на согласие возвращает ошибку?
- Пользовательский ввод экранируется с учётом формата получателя — спецсимволы имени не ломают разметку сообщения?
- Цели аналитики реально срабатывают на каждой форме, а не только объявлены?

Проверка цели: DevTools → Network → запрос к аналитике при отправке формы.
Идентификатор должен совпадать с тем, что шлёт код, символ в символ.

## Приём заявок — надёжность

- Сколько независимых каналов сохранения? Отказ одного не теряет заявку?
- «Принято» показывается только если заявка закрепилась хотя бы одним способом?
- Если не сработало ничего — код ошибки и запись в лог, а не молчаливый успех?
- Таймауты на внешние вызовы выставлены?
- Обработчик исключён из редиректов? Редирект на POST ломает отправку.

## SEO — расширенное

- `canonical` и JSON-LD корректны на **каждой** странице, не только на главной?

## Ссылки и редиректы

- Все внутренние ссылки ведут на существующие страницы?
- 301-редиректы реально срабатывают, старые адреса не отдают 404?
- Карта сайта совпадает со списком индексируемых страниц? `noindex`-страницы в неё не попали?
- Дубли закрыты: `/` и `/index.php`, слэш на конце, `www` и без?

**Проверять фактом.** Открыть `https://www.<домен>/<страница>` и убедиться, что
адрес сменился. Формулировка «настраивается на стороне хостинга» — красный
флаг: именно она однажды дала пункту годами проходить проверку при полностью
отсутствующем редиректе.

Редиректы строить на `THE_REQUEST`, а не `REQUEST_URI`, иначе они зацикливаются
с внутренними рерайтами. Правило `www` ставить до правила `http → https`.

## Маршрутизация

- Новая страница не называется именем существующей папки? Совпадение даёт конфликт с `mod_dir`.
- Между адресом со слэшем и без не стоит 301, если цель — директория? Это петля.
- `lastmod` в карте берётся из времени изменения конкретного файла, а не из даты сборки?

## Индексация

- Страница, закрытая мета-тегом `noindex`, **не закрыта** в `robots.txt`? Закрытую роботсом бот не прочитает и не увидит `noindex` — покажет голый URL.
- `Disallow` оставлен только для не-страниц: обработчик, конфиг, генератор, исходники?
- Архивная копия карты сайта закрыта, иначе бот примет её за вторую карту?

## Безопасность и надёжность

- `robots.txt` закрывает служебное? Правила без расширения работают как префиксные.
- Есть rate limiting на обработчике?
- Телефон валидируется на сервере?
- Нет токенов и паролей в публичном коде и в истории репозитория?
- `session_start()` стоит до любых заголовков и вывода?
- Ключ доступа к генератору живёт только в конфиге, не передаётся ссылкой?
- Сравнение секретов идёт за постоянное время?
- Несуществующий ключ отдаёт 404, а не 403 — чтобы не подтверждать существование файла?

---

## Сервер: кэш, сжатие, заголовки

- Включены gzip или Brotli, выставлены `Expires` и `Cache-Control` для статики?
- Есть кэш-бастинг для CSS и JS по времени изменения файла? Без него правка не доедет из-за длинного `Expires`.
- Заголовки безопасности заданы: `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, CSP, HSTS?
- Листинг каталогов закрыт?
- `.git` и служебные файлы недоступны по HTTP?
- Редирект `http → https` есть, с защитой от петли на SSL-прокси?
- Динамические страницы не кэшируются?

**Удаление файла не равно закрытию доступа.** Кэш хостинга может отдавать
вынесенный за вебрут файл ещё сутки. Как отличить кэш от файла на диске, не
заходя на сервер: запросить тот же адрес с произвольным query-параметром. Для
статического файла параметр ничего не меняет; если без него ответ есть, а с ним
нет — файла на диске уже нет, работает кэш. После выноса или удаления
чувствительных файлов проверять прямую ссылку и сбрасывать кэш.

## Медиа-целостность и CLS

- Каждый файл, на который ссылается код (`img`, `video`, `poster`), реально лежит на диске — нет 404 и нулевых файлов?
- У изображений заданы `width`/`height` или `aspect-ratio`?
- Фотографии не слишком тяжёлые, рассмотрена отдача WebP или AVIF?

- У непрерывных анимаций есть `will-change: transform`?
- У изображений `loading="lazy"`?

## Доступность

- У интерактивных элементов без текста есть `aria-label`?
- У изображений осмысленный `alt`?
- Модальные окна закрываются по `Escape`?
- Есть `<noscript>` там, где контент строится через JS?
- Есть `@media (prefers-reduced-motion: reduce)` — анимации мгновенные, автопрокрутка глушится отдельно через `matchMedia`?
- Контраст текста и фона достаточен по WCAG AA?
- Видны состояния `:focus-visible`, есть focus-trap в модалках и skip-to-content?

## PHP-надёжность

- `display_errors` выключен в проде, ошибки логируются?
- Переключатель по хосту, а не ручной?
- Мягко деградируют: пустой `glob()`, битый исходник, отсутствующая константа?
- Страница 404 подключена через `ErrorDocument` и отдаёт корректный код ответа?

---

## HTML-валидность и консистентность контента

- Нет дублирующихся `id` на странице? Критично — формы завязаны на ID.
- Ровно один `H1`, нет перескоков в иерархии заголовков?
- Телефон, цены, название бренда и реквизиты одинаковы на всех страницах?

## После правок

- Генератор перезапущен, если правки затрагивали ссылки, шаблоны, исходники или список страниц?
- Разовые диагностики окружения перепроверены, если окружение менялось?
- Правки залиты — деплой ручной, коммит в репозиторий его не заменяет?
