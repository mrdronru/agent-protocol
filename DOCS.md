# Документация проекта под работу с агентом

Агент читает документацию каждую сессию заново. Из этого следуют требования,
которых нет у документации для людей: человек помнит, что читал в прошлый раз,
агент — нет.

---

## Один входной файл с картой

В корне лежит `PROJECT.md`: общий слой, нужный в любой сессии, и карта — какой
файл читать под конкретную задачу.

```markdown
## Карта документа

- Правишь код, вёрстку, формы → `PROJECT-Сайт.md`
- Ищешь, что делать дальше → `TODO.md`
- Нужна предыстория решения → `HISTORY.md`
- Готовишь материалы и рекламу → `PROJECT-Продвижение.md`
- Ведёшь переписку и продажи → `PROJECT-Продажи.md`
```

Смысл разбиения: не читать всё целиком ради одной темы. Единый файл на несколько
тысяч строк съедает контекст и вытесняет то, ради чего сессия началась.

---

## Правила, которые окупаются

**Задачи живут в одном месте.** Единственный список по всему проекту. Задачи не
дублируются в тематических файлах — иначе через месяц два списка расходятся и
непонятно, какой настоящий.

**Не дублировать то, что уже есть.** Не вписывать в комментарий данные из
соседней колонки, не повторять в письме то, что адресату уже сказано, не
заводить второй файл по теме, у которой есть свой раздел. Экономия внимания
читателя важнее полноты изложения.

**Устаревшее переносится, а не удаляется.** Раздел, который перестал описывать
«как есть» и стал «как было», переезжает в `HISTORY.md` целиком. Причины
решений нужны позже — именно они не восстанавливаются из кода, и именно их
следующая сессия предложит «улучшить».

**Записывать по согласованию, а не на автомате.** Документ должен отражать то,
что реально согласовано, а не всё подряд, что происходило в сессии. Иначе он
наполняется черновиками и перестаёт быть источником истины.

---

## Источник истины — отдельная тема

Самая дорогая категория ошибок: агент делает вывод из файла, который не является
источником истины.

Три случая из практики.

**Сгенерированные файлы отстают от исходников.** HTML собирается скриптом из
Markdown, скрипт запускается на сервере. Локальные копии собранных файлов
систематически устарели. Судить по ним о состоянии системы нельзя — источник
истины это исходник и генератор. Аудит один раз отметил расхождение как
проблему; это не проблема, а устройство процесса.

**Локальная копия не содержит секретов.** Состав и структура файлов совпадают,
значения паролей и токенов — нет. Пустой пароль в локальном конфиге не значит,
что канал не настроен в продакшене. Если ответ зависит от значения секрета —
спросить человека, а не делать вывод из файла.

**Цены и подобные быстро устаревающие данные хранятся в одном месте.**
Продублированная в документацию цифра почти сразу начинает врать. В
документации — формулы, коэффициенты и структура; конкретные значения — в
единственном файле, на который все ссылаются.

Практический вывод: для каждой категории данных полезно один раз явно записать,
где источник истины и что является его производной.

## Журнал ошибок агента внутри документации

Отдельный раздел или файл, куда попадают сбои самого инструмента: глюки,
повреждения файлов, неудачные приёмы, ловушки окружения. Формат — в
[`ANTIPATTERNS.md`](ANTIPATTERNS.md).

Это работает не потому, что агент читает раздел и «исправляется», а потому что
человек перестаёт заново диагностировать ту же проблему через три месяца.
